# DHCP 动态主机配置协议

DHCP（Dynamic Host Configuration Protocol，动态主机配置协议）是网络中最基础也最常用的服务协议之一。

**应用层协议**，基于 UDP，用来给局域网主机自动分配 IP 地址、子网掩码、网关、DNS、租期等网络参数

## 为什么需要 DHCP？

手动配置静态 IP 有三个痛点：

- **工作量大**：成百上千台设备需要逐一配置，容易输错。
- **冲突管理难**：无法实时知道哪些 IP 已经被占用，容易分配冲突。
- **移动性差**：笔记本电脑从一个网络切换到另一个网络，必须手动修改 IP、掩码、网关和 DNS。

DHCP 让客户端可以从服务器**自动获得**：

- IP 地址与子网掩码
- 默认网关
- DNS 服务器
- 域名后缀等

这些参数以**租约**的形式授予，到期需要续租或释放，实现了 IP 地址的动态复用。

## DHCP 的四步握手：DORA 过程

客户端获取 IP 的标准流程是**四次交互**：Discover、Offer、Request、Acknowledge（简称 DORA）。

```text
客户端 (0.0.0.0:68)                  DHCP 服务器 (192.168.1.1:67)
        |                                    |
        |------ DHCPDISCOVER (广播) --------->|
        |<----- DHCPOFFER (单/广播) ----------|
        |------ DHCPREQUEST (广播) ---------->|
        |<----- DHCPACK (单/广播) ------------|
```

### Discover（发现）

- 客户端没有 IP，源地址为 `0.0.0.0`，目标为 `255.255.255.255`（广播）。
- 用 UDP 封装，源端口 68，目的端口 67。
- 报文可选携带 Option 55（Parameter Request List），告诉服务器“我需要子网掩码、网关、DNS 等”。
- 由于是广播，只有同广播域内的 DHCP 服务器或中继能收到。

### Offer（提供）

- 服务器收到 Discover 后，从地址池中选一个未被占用的 IP，**通过 ARP 或 ping 进行冲突检测**（部分服务器会做），然后发出 Offer。
- Offer 报文中包含：
  - **yiaddr**（分配给客户端的 IP）
  - **Option 1**（子网掩码）
  - **Option 3**（默认网关）
  - **Option 6**（DNS 服务器）
  - **Option 51**（IP 地址租约时间）
  - **Option 54**（DHCP 服务器标识符）
- Offer 可能是单播（目标 MAC 为客户端 MAC），也可能是广播（取决于客户端是否支持接收单播，由 Discover 的 Flag 字段决定）。

### Request（请求）

- 如果客户端收到多个 Offer（存在多台服务器），它通常选择最先到达的那个，然后广播 Request。
- Request **广播**的目的是通告所有服务器：“我已经接受了服务器 A 的 Offer，其他服务器的 Offer 可以回收了”。
- Request 中必须包含 **Option 54（服务器标识）** 指明自己选了哪台服务器，以及 **Option 50（请求的 IP 地址）**。

### Acknowledge（确认）

- 目标服务器收到 Request 后，确认 IP 仍可用，回复 ACK，正式确认租约。
- ACK 中再次携带全部配置参数，客户端收到后配置自己的网络接口。
- 如果服务器发现 IP 已被占用，回复 NAK（如客户端切换网络后仍请求原先 IP），客户端需重新开始 DORA。

## 地址租约管理与状态机

客户端获得 IP 不是永久的，需要一个状态机来管理生命周期。

```text
                +-----------+
                |   INIT    |  开始DHCP
                +-----------+
                      | 发送 DISCOVER
         +-----------v------------+
         |      SELECTING         | 等待 OFFER
         +------------------------+
                      | 收到 OFFER，发送 REQUEST
         +-----------v------------+
         |      REQUESTING        | 等待 ACK/NAK
         +------------------------+
         收到 ACK          收到 NAK 或超时
         |                     (回 INIT)
         v
    +---------+
    |  BOUND  |  租约生效，开启 T1, T2 定时器
    +---------+
      T1 到期         T2 到期           租约到期或收到 NAK
  (单播续租)       (广播重绑)             |
         |                |                |
   REQUEST->         REQUEST->             放弃 IP
   接收 ACK          接收 ACK               |
         |                |                v
         v                v             INIT
    回到 BOUND，    回到 BOUND，
    重置定时器      重置定时器
```

**关键时间点：**

- **T1（Renewal Time）**：默认租约的 50%。客户端开始**直接向分配 IP 的服务器**单播 REQUEST 续租。如果收到 ACK，租约延长并重置定时器。
- **T2（Rebinding Time）**：默认租约的 87.5%。如果 T1 续租失败，客户端开始**广播 REQUEST**，允许任何服务器响应。
- **租约到期**：若仍未成功，客户端必须停止使用该 IP，回到 INIT 状态，重新开始 DORA。

这个机制让系统在服务器短暂故障时仍能保持 IP 分配稳定，又把故障风险限制在一定时间内。

## DHCP 中继代理

DORA 过程依赖广播，而广播被路由器隔离。如果一个广播域部署一台 DHCP 服务器，成本太高。DHCP 中继就是为了**跨子网分配 IP**。

**工作流程：**

1. 客户端在子网 A 广播 DHCPDISCOVER（giaddr = 0.0.0.0）。
2. 子网 A 的路由器接口配置了 **ip helper-address**（Cisco）或 **dhcp-relay**（华为），充当**中继代理**。
3. 中继将收到的 DHCP 广播转为**单播**发往指定的 DHCP 服务器（源 IP 为中继接口 IP，目的为服务器 IP）。中继会修改报文：
   - `giaddr` 字段填上**自己接口的 IP**（即客户所在子网的网关接口 IP）。
   - `hops` 加 1。
4. 服务器收到请求，看到 `giaddr` 不为空，就知道该从 giaddr 所属的地址池中分配 IP。
5. 服务器将回复（OFFER/ACK）**单播给 giaddr 对应的中继接口**（中继的 UDP 67 端口）。
6. 中继收到后，再以**广播**或**单播**转发给客户端（取决于客户端的广播标志位，但因中继已经知道客户端 MAC，一般通过单播也可）。

## DHCP 协议握手发送时机

### Discover（发现）

1. 网卡刚启用、设备开机，网卡没有任何 IP 地址；
2. 曾经获取的 IP 租期完全到期，续约全部失败，IP 被剥夺；
3. 网络切换（WiFi 切换、网线拔插重新接入局域网）；
4. 手动释放 IP 后，重新请求地址。

### Offer（提供）

DHCP 服务器收到合法的 Discover 报文，地址池还有可用 IP，立刻回复 Offer。

### Request（请求）

**三种触发发送时机**

1. **DORA 流程中**：客户端收到 Offer，选择其中一台服务器，广播发送 Request，正式申请 IP；
2. **T1 时间点（租期 50%）**：**单播 Request 向原 DHCP 服务器续约**；
3. **T2 时间点（租期 87.5%）**：T1 续约失败，改为**广播 Request**，向网络中任意 DHCP 服务器请求地址。

### Acknowledge（确认）

#### ACK: 同意分配

DHCP 服务器收到 Request，同意分配 / 续约 IP，回复 ACK。

ACK 下发完整配置：IP、掩码、网关、DNS、租期。

客户端收到 ACK 之后，才正式启用 IP。

#### NAK: 拒绝分配

1. 客户端发送 Request，服务器发现该 IP 不可用、地址池耗尽；

2. 中继过来的请求，没有对应网段地址池；

   服务器回复 NAK，拒绝分配 IP，客户端必须重新发起 Discover。

### 其他情况

1. **DHCP Decline**

   客户端收到 ACK 拿到 IP，发送**免费 ARP 检测 IP 冲突**；

   发现网络中已经有设备在用这个 IP，立刻发送 Decline，告知服务器该 IP 冲突不可用，随后重新发起 Discover。

   > Decline 是**客户端检测到冲突之后才发出**，不是每次必现。

2. **DHCP Release**: 释放IP

   用户手动释放 IP、网卡禁用、设备正常关机(取决于**操作系统**和**关机类型**)，客户端主动单播向 DHCP 服务器发送 Release。

   服务器收到后，回收该 IP，放回地址池。

   > ⚠️ 异常断电、网线直接拔掉：**不会发送 Release 报文**，只能等待租期到期回收 IP。

3. **DHCP Inform**

   客户端已经拥有静态 IP，不需要申请 IP 地址，仅想要获取 DNS、域名后缀等配置参数；

   单播向 DHCP 服务器请求配置信息。企业环境多见，家用几乎看不到。

### 时间轴完整生命周期

1. 开机 / 插网线 → **Discover**\

2. 服务器应答 → **Offer**

3. 客户端 → **Request**

4. 服务器 → **ACK**

5. 客户端做免费 ARP，无冲突，使用 IP

6. 到达租期 50%(T1) → 

   单播 Request 续约

   - 成功：租期刷新；
   - 失败，等到 87.5%(T2) → **广播 Request 重绑定**

7. T2 依旧失败：等到租期到期，IP 作废，重新 Discover

8. 正常关机(取决于**操作系统**和**关机类型**) / 禁用网卡 → **Release**（异常关机无此报文）

## 快速重连: 记忆中有旧 IP

这个“快速重连”机制专门用来加快恢复速度

### 什么情况下会“记忆中有旧 IP”？

客户端不是凭空记住 IP 的，它通常发生在以下场景：

- **电脑正常重启**：系统关机前，DHCP 客户端程序会把当前租约信息（IP、掩码、网关、DNS、服务器标识、租约到期时间等）保存到硬盘或内存文件（如 Linux 的 `/var/lib/dhcp/dhclient.leases`，Windows 的注册表）。
- **网卡禁用后重新启用**：网卡被 `禁用` → `启用` 时，操作系统仍保留着之前的租约记录。
- **休眠/睡眠唤醒**：系统恢复时，网络栈重新初始化，但租约时间可能还没到。

**关键判断**：客户端会检查这份记忆中的租约是否仍然有效——即当前时间是否**早于租约到期时间**。如果已经过期，这份记忆就作废，直接丢弃并进入 INIT 状态，老老实实从头 DORA。

### INIT-REBOOT 状态的行为

如果旧租约**尚未过期**，客户端就会进入一个特殊的中间状态：**INIT-REBOOT**。

在这个状态下，客户端**跳过 Discover 和 Offer 阶段**，直接向网络广播一条 **DHCPREQUEST** 报文，内容是：

> “我想继续用我记忆中的 IP 地址 (比如 192.168.1.100)，我可以继续用吗？”

这条报文的关键字段：

- **源 IP**：仍然是 `0.0.0.0`（因为尚未正式绑定）
- **目标 IP**：`255.255.255.255`（广播，因为客户端不确定网络是否变化）
- **Option 50（Requested IP Address）**：填入记忆中的旧 IP，如 `192.168.1.100`
- **Option 54（Server Identifier）**：通常**不填**或填**旧服务器的 IP**（取决于实现）。根据 RFC 2131，在 INIT-REBOOT 中，客户端可以填入已知的服务器标识，但不是必需的。广播的目的是让任何合法服务器都能响应。
- **ciaddr**：客户端仍为 `0.0.0.0`，因为 IP 尚未最终确认。

### 服务器的三种可能回应

这条广播 Request 发出后，网络中的 DHCP 服务器（可能是原来的那台，也可能是别的）会根据情况给出三种回应：

#### 收到 DHCPACK → 快速回到 BOUND 状态

如果服务器认为该 IP 仍然合法可用（例如仍在地址池中，未被分配给其他客户端，且子网匹配），它会回复 **DHCPACK**。

ACK 报文中：

- **yiaddr** 还是那个旧 IP。
- 服务器可能会**更新租约**：重新给一个完整的租约期（相当于续租成功），或者保持剩余的租约时间不变。
- 同时携带子网掩码、网关、DNS 等配置。

客户端收到 ACK 后：

- 配置该 IP 到网卡，进入 **BOUND** 状态。
- 重置 T1、T2 定时器（基于新的租约时间）。
- 进行 ARP 探测（免费 ARP），确认无冲突。

整个过程只需**两次报文交互**，比完整的 DORA 省了一半时间。这就是我们重启电脑后网络连接恢复非常快的原因。

#### 收到 DHCPNAK → 放弃旧 IP，退回 INIT

如果服务器认为客户端**不能**再使用这个 IP，它会回复 **DHCPNAK**（否定确认）。

常见原因：

- 该 IP 已经分配给其他客户端（可能在你关机期间被别的设备拿走了）。
- 客户端移动到了另一个子网（比如笔记本从公司带到家里，旧 IP 是公司网段，家庭路由器无法识别）。
- 管理员从地址池中删除了这个 IP。

客户端收到 NAK 后：

- **立即停止使用** 旧 IP。
- 清除保存的租约信息。
- 状态从 INIT-REBOOT 转为 **INIT**。
- 然后**重新开始完整的 DORA 流程**：广播 Discover，寻求全新 IP。

#### 超时无响应 → 退回 INIT

如果客户端发送了 Request 后，在指定时间内**没有收到任何回复**（既没有 ACK 也没有 NAK）：

- 客户端会重试几次，仍无响应后，认定旧 IP 不可用。
- 同样清除租约记忆，转入 **INIT** 状态，开始新的 Discover。
- 这种超时处理跟从 REQUESTING 状态收不到回应类似。

### 对比 DORA

| 对比项       | 完整 DORA (初次获取) | INIT-REBOOT (重启获取) |
| :----------- | :------------------- | :--------------------- |
| 交互次数     | 4 次                 | 2 次（Request → ACK）  |
| 速度         | 慢，需等待服务器选择 | 快，网络几乎秒连       |
| 地址可能变化 | 可能拿到不同 IP      | 尽量维持原 IP 不变     |
| 适用场景     | 新设备、租约过期     | 重启、网卡重新启用     |

维持原 IP 的好处是：如果这个 IP 之前正在被某些应用程序使用（比如已建立的 TCP 连接虽已断，但应用层可能缓存了 IP），保持 IP 不变可以减少连接重设的麻烦。更重要的是，**网络恢复速度极快**，对用户体验非常友好。
